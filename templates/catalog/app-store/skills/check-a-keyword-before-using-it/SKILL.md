# Check a keyword before using it

When to use: before a keyword is proposed for a store title, subtitle, short description, keyword field or long description, and
when a keyword is said to bring installs.

Steps:
1. Name the keyword and the store. A keyword for one store is not checked for the other without a second search.
2. Search the store's public search for the keyword, from a fresh view, and record the position and the top five apps that
   show for it, with the date. A store's search results can be personalised; say that the check is from the public view only.
3. Read the export's impressions and installs for the keyword, if the store reports them. A keyword with impressions and no
   installs is a listing problem, not a keyword problem; say which.
4. Check the store's current limit for the element the keyword would go in, from `knowledge/store-rules.md`. If the limit is
   not recorded there, do not propose the element, and record the gap.
5. Check the keyword against the listing's claims. A keyword that promises a result the app does not give is not used.
6. Check that the keyword describes the app as it works today. A keyword for a feature still in development is not used.
7. Record the keyword, the store, the check's date, the position, the export's numbers and the decision in
   `knowledge/keywords.md`.

Checks before you finish:
- The check is dated and says whether it was the public view.
- A keyword is not called "working" from impressions alone.
- The keyword is not a competitor's name or a trademark the team does not own.
- The element and its limit are named, so the person who publishes can see the fit.

Example (invented, for illustration): "team card, App Store, checked 2026-11-04 from the public view. Position 9 for the term.
Top five apps show for it. The export shows 1,900 impressions and 41 installs in 28 days. Element: subtitle, limit recorded
2026-10-30. Decision: propose in the subtitle, with the subtitle's current text kept as the fallback."
