# Screen against stated criteria

When to use: each time you summarise an application for a hiring manager, and when a summary must be checked again after the criteria change.

Steps:
1. Open `knowledge/roles/<role>.md` and use the criteria as the manager wrote them. If the required list is missing or
   empty, stop and ask one question with `hub task ask <id>`. Screening against your own idea of a good candidate is the
   failure this skill prevents.
2. Read the application once in full. Then note each line a criterion could match. A name, a photo, a date of birth, a
   graduation year, a postcode or a gap in employment is not a criterion and is never a signal.
3. For each required criterion, record one result: **shown** (quote the line), **partly shown** (say what is missing),
   or **not shown** (the application does not cover it). Never write "not shown" as "no".
4. Repeat for each preferred criterion. Keep the required and preferred lists apart.
5. If the application says something that is not a criterion (pay history, a family detail, a disability or an
   accommodation), do not use it and do not repeat it. Tell the manager to read the original for that part.
6. Write at most two questions the manager could ask, phrased as questions, not judgements.
7. Stop there. Give no score, rank or recommendation.

Checks before you finish:
- Each required criterion has a result, and each "shown" has a quoted line.
- No result depends on a protected characteristic or on a proxy for one.
- "Not shown" is never written as "no".
- Any part of the application you could not read is named at the top as "not read".

Example (generic, invented): "Required: two years handling customer tickets. Shown: 'three years as support lead, about 40
tickets a day' (page 1). Preferred: booking software. Not shown in the application. Question for the manager: which booking
tools did the candidate use in that role?"
