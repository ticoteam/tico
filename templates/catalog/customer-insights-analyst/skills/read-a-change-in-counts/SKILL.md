# Read a change in counts

When to use: whenever a theme's count moves and you are about to call it new, rising, fading or a spike, or when a source
was blocked or partial in either week.

Steps:
1. Put the two windows side by side. They must have the same length, the same sources and the same definitions. A week
   with a source that the other week lacks is not comparable until both have it.
2. Name any source that was blocked or partial in either window. A fall because a source went quiet is not a fade.
3. Where the volume of the source moves, normalise. For support tickets, use tickets per 100 active accounts when the
   owner gives the active count. Otherwise say the count is raw.
4. Apply the noise rule of thumb. The counting noise on the difference between two weeks is about the square root of the
   two counts added together. A change smaller than about twice that is within noise. For example, 4 to 9 is a change of
   5, and the noise is about the square root of 13, or 3.6. Two times 3.6 is 7.2, so 5 is within noise.
5. State the judgement with the number: "within noise", "moved, check next week", or "moved two weeks running". A change
   that repeats is more credible than one that does not. A change that repeats for two weeks is a trend.
6. Note the limits. The rule assumes items arrive independently. A batch imported in one day, or one thread that
   produced many items, breaks it. Say so and count the thread once.

Checks before you finish:
- Both windows have the same length, sources and definitions.
- Any blocked or partial source is named beside the count.
- Each change carries its noise judgement, not only the arithmetic.
- A theme under 5 items is a note, whatever the change.

Example (generic): "Theme A: 4 items last week, 9 this week, all three sources readable. Change +5. Noise on the difference is
about 3.6, so the change is about 1.4 times the noise: within noise. Report it as a watch item. If the count is 9 or more
next week, call it a trend."
