# Task worktrees

A task worktree gives a bot a separate branch and folder for its code work. The computer shares one base clone per repository and records each worktree on its task.

During a bot run:

```sh
hub task worktree add org/product
hub task worktree attach tasks/12345678/org__product
hub task worktree setup org/product
```

The commands use the run's current task. Add `--task <id>` to choose another task owned by the same bot. The local MCP tools are `hub_task_worktree_add` and `hub_task_worktree_attach`.

With a GitHub App connected, the bot needs write access to the repository. A human who can move tasks can request a worktree through `POST /api/v2/tasks/{id}/worktrees`; the computer creates it on its next heartbeat while that bot is idle. Creation returns the link, branch and path. Folders are under `<workspace>/tasks/<task-short>/<repository-owner>__<repository-name>`, with branches named `tico/<task-short>-<task-title>`.

Before creation, the computer makes a quick, bounded attempt to refresh the mirror from GitHub, then refreshes the base clone from that mirror. If GitHub is unavailable, creation uses the cached mirror and reports its age. A new link records `checkout_state=queued` before Git materializes the checkout, then records the expected commit and target before `git worktree add`. Heartbeats keep the link pending until checkout and setup both finish; a directory with `.git` alone is not a ready worktree. Setup commands run only during a bot run, with process and language toolchain settings. They receive no Tico token, GitHub token, credential socket or credential grants. Setup that needs network authentication fails with a message explaining that credentials are unavailable. `add` runs setup for a new tree. A setup failure or interrupted setup leaves the link pending with setup explicitly retryable through `hub task worktree setup <repo>`. A timeout stops the setup process and its children. Creation and restoration share a path lock with bot commands. Adding during a pending restoration reuses the same link.

An interrupted add resumes automatically only when its task link says initialization was in progress and the saved repository, task branch, base path and expected commit still match. If that exact worktree has only unstaged tracked-file deletions, Tico restores those missing paths from the recorded commit. Any modification, staged change, untracked file, different commit, branch, repository or common Git directory keeps the checkout untouched and pending. A queued link with an already existing path is also left untouched. Existing legacy links without an initialization record are not rewritten based on file deletions; a person must inspect their status and history and choose a separate replacement path if needed. Keep the old directory until its changes have been reviewed and preserved.

Attach accepts an existing Git worktree inside the team workspace whose base is also there. The command checks its repository and branch. Paths cannot pass through symlinks or the base-clone folder `repos`. Equivalent paths, including differences in letter case, cannot belong to different tasks. After a task is reassigned, its new owner can reuse a removed worktree link; if the previous owner still has a worktree awaiting cleanup, Add creates a separate folder and branch. A folder under `tasks/<task-short>/` can only attach to that task. A path-only API attachment awaits the computer's report to identify its repository and branch and verify write access.

The computer reports the current branch, unpushed commits, changed files, last commit and size with its heartbeat. The link's task branch stays fixed; the current branch is in its detail. Ahead and behind compare with the task branch on origin, falling back to commits absent from origin when that branch has no tracking ref. Normal pushes update the task branch's tracking ref. Size and file activity refresh at most every ten minutes. Health shows disk use and worktree errors. A worktree missing for a day, or with unpushed commits and no activity for three days, wakes its task's bot once until the condition changes.

Closing or finishing a task removes its worktrees after every attached PR is merged, closed or shipped. Archiving a bot also cleans up its worktrees when its PRs are finished. The computer waits until that bot's runs finish; other bots can keep working. A turn renews its lease while waiting for maintenance. Maintenance and turns for the same bot share a lock, and cleanup checks again immediately before removal that the task is still closed and the bot is idle. It saves changed files in a commit on `wip/<task-short>-<link-short>` and pushes before removal. If the task reopens before removal, it switches back to the task branch with the saved work. It never moves the task branch backwards or replaces separate history. Clean finished-PR trees save any unpushed commits to the snapshot branch without recreating deleted PR branches. Detached worktrees also preserve unpushed work in snapshots. Other clean trees preserve unpushed task-branch commits before removal. The default branch is never pushed by cleanup.

Cleanup keeps the folder if saving or pushing fails. It also keeps trees containing likely secret files (`.env*`, `*.pem`, `*.key`, `id_rsa*`, `credentials*`, `*.p12`), changed files larger than 20 MB, possible secrets in changed or untracked files, including that bot's most recent granted credential values, or ignored files outside common build folders. Skipped files are listed in the link's detail. Ignored files in `node_modules`, `.venv`, `venv`, `dist`, `build`, `target`, `.next`, `__pycache__`, `.cache` and `coverage` may be removed with the tree. The secret check runs before switching branches or staging, so a refusal leaves HEAD, the index and files unchanged. Python caches (including `*.pyc` and `*.egg-info`), `.DS_Store`, `.idea`, `.vscode`, `.tox`, `.gradle` and `.terraform/providers` caches may also be removed. Health reports the reason a tree was kept. Failed actions retry with a delay starting at five minutes and increasing to six hours; retries during that delay do not mint tokens.

Reopening restores only trees that were present when the task closed and were removed by cleanup. A deliberately removed tree or failed bot creation is left alone. Restoration uses local task history, a newer saved snapshot that contains that history, origin's task branch, or origin's default branch. Saved snapshots are recovered even after the base clone was removed; older `wip/<task-short>` snapshots remain supported. When a remote lookup fails, available local task history can still be restored offline. Without local history the failure keeps restoration pending. A snapshot with separate history is recorded as `snapshot_skipped` in the link's detail. Stale worktree registrations are pruned before creation and removal.

Removing a worktree link needs the same rights as changing the task. Its folder is cleaned up before the link disappears. Reassigning a task preserves the worktree's original bot and computer for cleanup. Cleanup credentials cover only the tracked repository within that bot's current write grants; they are never written to disk. Git maintenance disables repository hooks, fsmonitor and optional index locks and receives only filtered process settings and its scoped GitHub helper.

A bot can have up to ten worktrees awaiting cleanup, including worktrees on reassigned tasks. Adding or restoring a worktree needs at least 5 GB free. Finish or close older tasks to free worktrees, and free space on the workspace volume if creation reports low disk. Unselected managed base clones, including clones created for a bot's own repository, are tracked for 30-day cleanup. Before retirement, stale registrations are pruned. Bases with live task worktrees, uncommitted or untracked files, or unpublished branch, stash or detached-HEAD commits are kept for repair or later cleanup. A local branch can retire when all its commits are on a remote, even under a different branch name. Missing path-only worktrees are marked removed and stop counting toward the limit.

Older computers keep running bots normally. They report worktree state as unknown and creation says “Update this computer to use task worktrees”. A new computer talking to an older server omits optional heartbeat fields, and the worktree commands say the server needs updating. A rejected worktree report is retried without that optional field so the computer remains online. Update the server first, with the task-link schema, then computers.

The runner confirms worktrees through `PATCH /api/v2/tasks/{id}/links/{link_id}`. Only the registered computer or the owner bot on that computer can confirm a tracked worktree. Heartbeat actions are retried until the computer reports completion.

## Without a GitHub App

On a Mac using the native runner, or a local Docker computer, worktrees can use the computer's own Git login. Run `hub task worktree add org/product`, or supply a full HTTPS or SSH Git URL. The computer clones directly into `<workspace>/repos/<owner>__<repo>` and creates the task worktree. URL addresses get a stable folder suffix to keep hosts and addresses distinct. No mirror or App token is needed. For Docker, the Git login and SSH agent must be available inside the computer's container.

Task ownership, the ten-worktree limit and disk checks still apply. Cleanup, restoration and saved-work pushes use the same computer Git login. A connection failure says `git could not reach org/product with this computer's git login:` followed by the first error line. Git maintenance still disables repository hooks and fsmonitor, ignores repository Git programs and filters its environment; it keeps the computer's system and global credential settings, URL rewrites, SSH command, HTTP proxy and CA settings, and Git identity (without config includes). Connecting a GitHub App uses the App repository grants and scoped tokens as usual.
