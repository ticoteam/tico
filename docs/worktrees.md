# Task worktrees

A task worktree gives a bot a separate branch and folder for its code work. The computer shares one base clone per repository and records each worktree on its task. Each task session also runs in its own worktree of the bot's own repository ([Sessions](sessions.md#many-tasks-at-once)).

During a bot run:

```sh
hub task worktree add org/product
hub task worktree attach tasks/12345678/org__product
hub task worktree setup org/product
```

The commands use the run's current task. Add `--task <id>` to choose another task owned by the same bot; an abbreviated task ID is resolved to its canonical ID before any worktree operation. The local MCP tools are `hub_task_worktree_add` and `hub_task_worktree_attach`.

With a GitHub App connected, the bot needs write access to the repository. A human who can move tasks can request a worktree through `POST /api/v2/tasks/{id}/worktrees`; the computer creates it on its next heartbeat while that bot is idle. Creation returns the link, branch and path. Folders are under `<workspace>/tasks/<task-short>/<repository-owner>__<repository-name>`, with branches named `tico/<task-short>-<task-title>`.

Before creation, the computer makes a quick, bounded attempt to refresh the mirror from GitHub, then refreshes the base clone from that mirror. If GitHub is unavailable, creation uses the cached mirror and reports its age. A new link records `checkout_state=queued` before Git materializes the checkout, then records the expected commit and target before `git worktree add`. Heartbeats keep the link pending until checkout and setup both finish; a directory with `.git` alone is not a ready worktree. Setup commands run only during a bot run, with process and language toolchain settings. They receive no Tico token, GitHub token, credential socket or credential grants. Setup that needs network authentication fails with a message explaining that credentials are unavailable. `add` runs setup for a new tree. A setup failure or interrupted setup leaves the link pending with setup explicitly retryable through `hub task worktree setup <repo>`. A timeout stops the setup process and its children. Creation and restoration share a path lock with bot commands. Adding during a pending restoration reuses the same link.

An interrupted add resumes only when the task link and a local initialization marker identify the same task, path, repository, branch, base clone, target and expected commit, and the exact worktree is clean. The marker records checkout phases locally; the service stores only a hash of the base-clone path. Setup starts after checkout completion is recorded. Tico never restores missing files based on deletion-only status: any changed or incomplete worktree stays untouched and pending. A queued link with an existing path, a different base clone, or a mismatched marker is also left untouched. The add response includes the link's persisted state; a missing state is never treated as present. A legacy link already recorded as `present` remains present only while its registered repository and branch match, setup is complete, and no tracked files are missing; this compatibility state does not create a new completion marker or upgrade a pending link. Dirty or untracked legacy work is retained. Missing tracked files and ambiguous legacy paths remain unverified; `hub task worktree setup` does not promote them.

There is no automatic in-place repair for a dirty, partial or legacy tree. Keep its directory and branch unchanged while a person reviews the task link, Git status and history and preserves any wanted local edits. If a replacement is chosen, create it at a separate sibling path from a human-verified local source branch, using a unique recovery branch, then attach that completed worktree:

```sh
git -C "$HUB_WORKSPACE/repos/<owner>__<repo>" worktree add -b "recovery/<task-short>-<suffix>" \
  "$HUB_WORKSPACE/tasks/<task-short>/recovery-<suffix>" <verified-source-branch>
hub task worktree attach "tasks/<task-short>/recovery-<suffix>" --task <task-id>
```

This leaves the original tree and branch in place; copy or apply selected uncommitted changes only after review. Do not reset, prune or retry `add` or `setup` against the original path to recover it.

Attach accepts an existing Git worktree inside the team workspace whose base is also there. The command checks its repository and branch. Paths cannot pass through symlinks or the base-clone folder `repos`. Equivalent paths, including differences in letter case, cannot belong to different tasks. After a task is reassigned, its new owner can reuse a removed worktree link; if the previous owner still has a worktree awaiting cleanup, Add creates a separate folder and branch. A folder under `tasks/<task-short>/` can only attach to that task. A path-only API attachment awaits the computer's report to identify its repository and branch and verify write access. Before reporting it present, the computer verifies the worktree registration and repository, confirms the task branch/base, and records a local readiness marker. If tracked files are missing before this initial proof exists, it remains pending and unverified; the original path is preserved and no files are restored. Dirty edits and untracked files are preserved when the existing checkout can be verified. Use the separate sibling-worktree recovery path above when completion cannot be established.

The computer reports the current branch, unpushed commits, changed files, last commit and size with its heartbeat. The link's task branch stays fixed; the current branch is in its detail. Ahead and behind compare with the task branch on origin, falling back to commits absent from origin when that branch has no tracking ref. Normal pushes update the task branch's tracking ref. Size and file activity refresh at most every ten minutes. Health shows disk use and worktree errors. A failed restore or prepare stops counting once the worktree is set up and reported ready; a refused cleanup counts while cleanup is asked, including after the computer restarts, and is forgotten once the task reopens. A failure the computer sees in the tree itself is shown ahead of an earlier failed action. A worktree missing for a day, or with unpushed commits and no activity for three days, wakes its task's bot once until the condition changes.

When all attached pull requests are merged, closed or shipped, clean worktrees with nothing unpushed are released without waiting for the task to be Done; release and post-release QA can continue. Dirty or unpushed work stays with the reason shown on the task.

Closing or finishing a task removes its worktrees after every attached PR is merged, closed or shipped. Archiving a bot also cleans up its worktrees when its PRs are finished. The computer waits until that bot's runs finish; other bots can keep working. A turn renews its lease while waiting for maintenance. Maintenance and turns for the same bot share a lock, and cleanup checks again immediately before removal that the task is still closed and the bot is idle. It saves changed files in a commit on `wip/<task-short>-<link-short>` and pushes before removal. If the task reopens before removal, it switches back to the task branch with the saved work. It never moves the task branch backwards or replaces separate history. Clean finished-PR trees save any unpushed commits to the snapshot branch without recreating deleted PR branches. Detached worktrees also preserve unpushed work in snapshots. Other clean trees preserve unpushed task-branch commits before removal. The default branch is never pushed by cleanup.

Cleanup keeps the folder if saving or pushing fails. It also keeps trees containing likely secret files (`.env*`, `*.pem`, `*.key`, `id_rsa*`, `credentials*`, `*.p12`), changed files larger than 20 MB, possible secrets in changed or untracked files, including that bot's most recent granted credential values, or ignored files outside common build folders. Skipped files are listed in the link's detail. Ignored files in `node_modules`, `.venv`, `venv`, `dist`, `build`, `target`, `.next`, `__pycache__`, `.cache` and `coverage` may be removed with the tree. The secret check runs before switching branches or staging, so a refusal leaves HEAD, the index and files unchanged. Python caches (including `*.pyc` and `*.egg-info`), `.DS_Store`, `.idea`, `.vscode`, `.tox`, `.gradle` and `.terraform/providers` caches may also be removed. Health reports the reason a tree was kept. A tree stopped mid-merge is checked before anything else: if the merge was abandoned (every conflicted file still holds only Git's own conflict markers, nothing is resolved or edited, and the other staged files already match the merged branch), cleanup aborts the merge and continues as usual. Anything else is kept with the reason "merge in progress" and nothing in the tree is changed.

Once a closed task's worktree under `tasks/<task-short>/` is removed and no other live worktree uses that folder, the computer also deletes what can be rebuilt there: Python virtual environments (`pyvenv.cfg`), folders marked with `CACHEDIR.TAG` (such as Cargo `target` and `.pytest_cache`), `node_modules` and pytest temp folders. It also removes extra Git worktrees in the folder that have no changed or untracked files, no commits missing from origin, and no ignored files outside build folders. Logs, notes and other files stay. A checkout with unsaved or unpushed work stays as it is, and symlinks are never followed.

A refused cleanup is not retried forever. After the computer refuses, the server asks it again at most six times, waiting 2, 4, 8, 16 and 32 minutes between asks, and stops asking 64 minutes after the sixth, about two hours after the first refusal. The link's detail then shows `cleanup_gave_up`, with `cleanup_attempts` at 6, and Health shows the refusal; the folder and its files stay where they are. Separately, the computer waits before it repeats any failed action on a worktree (restore, prepare or cleanup): five minutes after the first failure, doubling to at most six hours. An ask that arrives during that wait is skipped, so only about three real attempts run. Retries during that wait do not mint tokens.

Reopening restores only trees that were present when the task closed and were removed by cleanup. A deliberately removed tree or failed bot creation is left alone. Restoration uses local task history, a newer saved snapshot that contains that history, origin's task branch, or origin's default branch. Saved snapshots are recovered even after the base clone was removed; older `wip/<task-short>` snapshots remain supported. When a remote lookup fails, available local task history can still be restored offline. Without local history the failure keeps restoration pending. A snapshot with separate history is recorded as `snapshot_skipped` in the link's detail. Stale worktree registrations are pruned before creation and removal. Person-created pending links receive restore actions until the runner records checkout progress; once progress or setup failure is recorded, the server waits for explicit setup retry instead of requesting restore again.

Removing a worktree link needs the same rights as changing the task. Its folder is cleaned up before the link disappears. When cleanup has stopped asking, a person (or the owning bot) first fixes the cause the refusal names. For "This bot needs write access to save its worktree", give the owning bot write access to the repository again. For kept files, review the files listed in the link's detail and move or delete the ones that should not stay. For "merge in progress", finish the merge in the folder: commit the resolved files, or abort it with `git merge --abort` if its changes are not wanted. For "resolved or unrecognised conflicts", commit or abort it the same way. Then choose **Retry cleanup** on the worktree in the task's Code list; it appears, for people who can move tasks, on a worktree whose cleanup stopped retrying. It sends the same request as removing the link again with `DELETE /api/v2/tasks/{id}/links/{link_id}`, which BotOps can send for you and a bot that owns the task can send itself. A released worktree of an open task is not offered the button: its cleanup resumes by itself when its work changes, such as a new commit, a changed file or a push of its unpushed commits. This starts a fresh bounded cleanup on the link's original computer, with the six-ask schedule above starting over. A removed link is not restored if the task reopens; work that cleanup saved stays on its `wip/` snapshot branch. Do not edit the database or the worktree's Git files to clear the stop. An updated Rust computer recognizes each explicit request once, after the bot is idle and its locks are available; repeated heartbeats still respect a new refusal's backoff. The last refusal can clear before the new attempt reports, for example after the computer restarts; the link goes only once the folder is removed, and files are still saved or kept by the normal safety checks. Reassigning a task preserves the worktree's original bot and computer for cleanup. Cleanup credentials cover only the tracked repository within that bot's current write grants; they are never written to disk. Git maintenance disables repository hooks, fsmonitor and optional index locks and receives only filtered process settings and its scoped GitHub helper.

A bot can have up to 100 worktrees awaiting cleanup, including worktrees on reassigned tasks. This is separate from concurrent-run capacity. Adding or restoring a worktree needs at least 5 GB free, so a full disk stops it sooner. Nothing is removed to make room. At the limit, `hub task worktree add` in the bot's own turn on that task records that the task waits for a worktree, prints why, and exits with status 3: the bot ends its turn instead of waiting, which lets its finished worktrees free themselves. When a place frees, Tico reserves the worktree (checking the bot's repository access, the task's owner and its computer again), the computer checks it out and runs setup while the bot is idle, and once it is present and set up Tico wakes the task once, in its own session, naming the worktree. A failed checkout or setup wakes it once with the reason. The wait ends without a wake when the task finishes or changes owner or a person stops the turn that asked. The task and Health show "Waiting for a worktree" with its age. A person's request, an attach, or a computer from before this change gets the old answer instead: creation names the oldest idle worktrees, and the bot or a person cleans one up first. Free space on the workspace volume if creation reports low disk. Unselected managed base clones, including clones created for a bot's own repository, are tracked for 30-day cleanup. Before retirement, stale registrations are pruned. Bases with live task worktrees, uncommitted or untracked files, or unpublished branch, stash or detached-HEAD commits are kept for repair or later cleanup. A local branch can retire when all its commits are on a remote, even under a different branch name. Missing path-only worktrees are marked removed and stop counting toward the limit.

A worktree is released by its task's pull requests, so Tico keeps those links itself. A pull request whose head is a task worktree's branch (`tico/<task>-...`) in the same repository is linked to that task when GitHub reports it, with no wake, for every repository the task has a worktree in; a fork's branch never is. Every few minutes, a bounded background pass also re-reads the unfinished pull request links of every task that holds a worktree, closed, declined and unread ones included, and asks GitHub for a pull request on any worktree branch that has none, so a missed webhook heals without anyone opening the task. A worktree whose branch has pushed commits of its own (not just newer main) and no pull request linked on that branch is held, not released, and says why ("held: commits on ... with no pull request linked"); moving its task to any review step, or to done, is refused with the repository and branch named, until the pull request is opened or linked with `hub task link`. A branch the background pass can read is also held, and a hand-off refused, until that pass has read it on GitHub since its last commit or push, so a push whose webhook was missed and that no computer has reported yet still counts; this clears within a few minutes, or at once when the pull request is linked. A worktree branch with commits of its own on GitHub also gets a draft pull request within a few minutes if none exists, even when the push webhook was missed, titled after the task (a private task's after its branch) and linked the same way; `gh pr create` then reports the branch already has one, so edit it with `gh pr edit` and mark it ready with `gh pr ready`. If opening or linking the draft fails, the worktree shows the reason until the branch's pull request is linked, and the next pass tries again. Pushing and the pull request's checks are never held back for a link. A released worktree can still be asked for again with `hub task worktree add` when its task needs more work. Reusing a removed link starts a new allocation and clears its old release, cleanup and removal state. While the task is at a working step (`doing`), a PR from before that allocation cannot release the new tree; a PR opened for that allocation can. Review-step tasks retain the usual cleanup once all their PRs finish.

A new worktree starts only for work a coding step can run on now: `hub task worktree add` is refused, with the reason, for a task still `open` (On Deck or not started: move it to In Progress first), one blocked by a task whose code is not merged yet (the blocker is named, with its step and any unmerged pull request), and a done, closed or declined one. A worktree builds from source, so a blocker stops holding it once its code is merged, not once it ships: at its type's Pending Release step or a later one (Post Release QA), at a `ready` status, or when it has a merged pull request and none still open (one closed without merging was abandoned and does not count). A done, closed or declined blocker never holds it. A task in progress, or at a review or waiting step while a fix-forward or review fix runs on it, gets one, and so does reassigned work. A task waiting for room is checked again before its place is reserved and before its computer prepares it: a task blocked or finished since it asked gets no tree and no wake. A worktree whose task's pull requests are all finished is not released while its bot, as the task's owner, is in a turn on that task ("held: live turn"; another bot's turn on the task, such as a reviewer's, does not hold it) or while its pushed branch has commits past the head of the last finished pull request on it ("held: new commits since PR #N"), so a fix-forward after a merge keeps its tree; both clear by themselves when the turn ends or a new pull request carries the commits and finishes. In rarer cases a released tree may still need asking for again. A `pending` worktree that is no longer needed (its task finished, or all its pull requests finished, with no turn or waiting task holding it) is cancelled: when nothing was checked out its place frees at once and nothing on disk is touched; otherwise the computer removes it with the usual checks, keeping unsaved work. A `pending` worktree whose checkout or setup makes no progress for 6 hours, with no turn of its owner on its task, has failed (unless it is released in that same pass because its pull requests finished, which sends no retry message): it keeps its place and shows "Setup did not finish within 6 h", its computer stops preparing it, a waiting task's wait ends, and the owner is told once; The message names the retry for the same worktree (same path and branch): `hub task worktree setup <repo>` when a checkout was made, which resumes it in place and re-runs setup there, or `hub task worktree add <repo>` when nothing was checked out yet. A push webhook whose head differs from the merged head holds the tree only until the computer's next report after that delivery: a clean report with nothing unpushed at the merged head proves the push stale (a delayed or replayed delivery), so it is cleared and the release names it; a later push clears that note again. Every release adds a `worktree.released` event to the task naming the reason (pull request merged, pull request closed, task finished, pending cancelled, and the `wip/` branch when a finished task's unsaved work was saved), and Health lists the last day's releases by reason.

Older computers keep running bots normally. They report worktree state as unknown and creation says “Update this computer to use task worktrees”. A new computer talking to an older server omits optional heartbeat fields, and the worktree commands say the server needs updating. A rejected worktree report is retried without that optional field so the computer remains online. Update the server first, with the task-link schema, then computers.

The runner confirms worktrees through `PATCH /api/v2/tasks/{id}/links/{link_id}`. Only the registered computer or the owner bot on that computer can confirm a tracked worktree. Heartbeat actions are retried until the computer reports completion.

## Without a GitHub App

On a Mac using the native runner, or a local Docker computer, worktrees can use the computer's own Git login. Run `hub task worktree add org/product`, or supply a full HTTPS or SSH Git URL. The computer clones directly into `<workspace>/repos/<owner>__<repo>` and creates the task worktree. URL addresses get a stable folder suffix to keep hosts and addresses distinct. No mirror or App token is needed. For Docker, the Git login and SSH agent must be available inside the computer's container.

Task ownership, the 100-worktree limit and disk checks still apply. Cleanup, restoration and saved-work pushes use the same computer Git login. A connection failure says `git could not reach org/product with this computer's git login:` followed by the first error line. Git maintenance still disables repository hooks and fsmonitor, ignores repository Git programs and filters its environment; it keeps the computer's system and global credential settings, URL rewrites, SSH command, HTTP proxy and CA settings, and Git identity (without config includes). Connecting a GitHub App uses the App repository grants and scoped tokens as usual.
